# AI 审查依据

AI 审查 PR 改了什么，以及候选合并后的代码，判断可能的上线风险。输入包括实际 diff、固定 candidate SHA 的源码切片、受保护 base 的架构契约，以及 base/candidate 的累计债务账本。

## 审查方法

- 沿入口、认证、授权、资源归属、数据访问和外部调用追踪行为，说明变更前后差异、触发条件、失败或攻击路径及影响范围。
- 结合候选态已有代码分析组合风险：权限绕过、跨用户或租户访问、凭据泄露、注入、文件边界、事务和幂等、错误语义、生产默认配置、依赖使用及 CI 信任边界。
- 风险必须定位到可观察的源码和行为；未知运行时信息写“未提供”。PR 正文是作者声明，不能替代源码分析。
- 测试或扫描结果缺失本身不构成阻断理由，也不计入技术债。关键代码缺失或 diff/源码不完整而无法完成审查时，明确说明缺口并 `BLOCK`。
- 不安装项目依赖、不执行 PR 代码、不采集独立 CI 或扫描结果。不得编造已经运行的测试、扫描、请求/响应或漏洞数据库信息。

## 候选态和规则边界

`pull_request` 绑定 `base_sha + head_sha + merge_sha`；`merge_group` 绑定 `base_sha + queue_parent_sha + merge_sha`。发布报告前复核 SHA，漂移时旧结论失效。

候选源码包括契约覆盖的路径和本次变更中仍存在的文件。新增依赖边、依赖环、资源规则、组合规则和债务预算由静态架构逻辑判定；AI 使用同一候选态分析业务上线风险。删除文件通过 diff 审查。树截断、源码超限或无效契约应 fail closed。

契约修改仍按受保护 base 版本评估；负责人审批由目标项目的 CODEOWNERS 和 GitHub 合并规则执行。债务条目删除只表示“声明已解决”，AI 应结合候选代码复核修复依据。
