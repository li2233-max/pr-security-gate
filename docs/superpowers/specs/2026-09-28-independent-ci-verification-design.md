# CI 配置变更的独立验证设计

日期：2026-09-28

状态：方案方向已确认；本文等待用户审阅。尚未实施，不代表任何 PR 已通过或获准合并。

## 1. 目标与现状

用户希望修改 CI 的 PR 也能取得可信的测试和扫描证据，同时不能通过修改自己的检查规则绕过门禁。

现有门禁在 PR 修改 `.github/workflows/` 或 `.github/actions/` 时拒绝本次所有普通 Actions Check。`weixin` PR #4 已出现扫描和测试通过、证据仍不受信的情况；加入支付回调修复后，还触发支付关键路径的可信测试要求。单独拆分 CI PR 并不能自动解决这个首次接入问题。

本设计新增一个受中心版本约束的独立验证来源，不移除普通 CI 的拒绝规则。安全审查、架构契约、技术债策略仍独立裁决，独立验证通过不等于整个 PR 自动 PASS。

成功标准：CI 改动不能控制验证命令或伪造结果；真实通过且来源、版本、候选 SHA 均核验成功时可以提供证据；任一必需检查失败、跳过、缺失或过期仍 BLOCK。

## 2. 选定方案与范围

选定：中心仓库提供固定提交的可复用验证器，在目标项目的 GitHub-hosted runner 上运行；独立验证不传入业务 Secret，不使用跨仓库 PAT，不把私有源码上传到中心仓库。

不选择另建 GitHub App/外部验证服务：本阶段避免额外服务、私钥和权限维护。也不采用“负责人评论同意就把检查标成通过”：人工审核不能伪造机器扫描结果。

首期支持 `li2233-max/weixin` 的普通同仓库 PR 与 `merge_group`，并保持现有普通 PR 路径兼容。其他仓库、fork PR、手工 dispatch 不能套用这个项目的验证配置，未接入时按不支持/证据不足处理。

不包含：自动合并、放宽 required checks、修改付费套餐或仓库权限、业务功能开发、自动接受 AI 技术债、保证抵御仓库管理员或中心信任根被攻陷。

## 3. 信任根与版本发布

中心验证器版本记为 V，采信它的中心审查器版本记为 G；两者均指完整 40 位提交 SHA，而不是分支或可移动标签。

1. 先独立审核和发布 V：包括可复用验证工作流、可信启动器、固定扫描规则、验证配置、关键测试资产和项目入口模板。
2. 再发布 G：在中心策略中登记 V、验证器路径、调用模板、项目身份、验证配置及允许的证据映射。
3. 目标 PR 只能调用 G 已登记的 V。增加新 V 必须先走中心仓库审查，不能通过目标 PR 的输入、变量或配置自行登记。

分开发布避免“提交中写入自身 SHA”的循环。回滚只允许使用中心仍明确批准的完整 SHA，不能自动退回某个历史标签。

中心 main 的审批与目标项目合并保护是部署前提。此前出现过私有仓库 Ruleset 不执行的提示，验收必须检查其实际生效状态。若平台不能强制保护，只能说明本方案提供可信验证与人工合并纪律，不能宣称已经强制阻止所有绕过。不得擅自升级套餐、改公开性或删除保护规则。

目标 PR 可修改审查入口本身，因此必须审核其确实调用已批准 G；本方案不以“同名绿色 pr-security-gate”代替这一要求。要对不可信 PR 作者强制执行，需受保护的工作流/外部执行约束；普通 required-check 名称本身不是对工作流来源的密码学证明。

## 4. 组件与调用约束

| 组件 | 职责 | 不得接受的控制输入 |
| --- | --- | --- |
| 项目独立入口 `.github/workflows/independent-ci-verification.yml` | 监听 PR/合并队列，仅调用固定 V | 任意 steps、脚本、matrix、条件跳过、Secret 继承 |
| 中心验证器 `.github/workflows/independent-ci-verification.yml` | 解析候选身份、调度检查、生成结构化结果 | 调用方指定的命令、源码 ref、扫描配置、测试路径 |
| 中心项目验证配置 | 固定扫描范围、工具版本、关键测试资产及证据能力 | 候选 PR 自己改写的“可信配置” |
| 中心证据采集器 | 核对 GitHub 来源、结果和当前 SHA，映射证据 | 作者声明、同名检查、未核验 artifact |
| 原有 AI/架构审查器 | 消费可信证据并作最终裁决 | 独立验证结果覆盖契约/债务规则 |

独立入口采用中心生成的完整规范模板：仅允许 LF/CRLF 换行等价，不进行宽松 YAML 语义匹配。事件、权限、job ID、固定 `uses` 和允许字段都必须精确匹配；额外 job、环境变量、输入、YAML 重复键、锚点或表达式均不被接受。模板中的 V 由 G 的策略填充，不来自 PR 声明。

入口可以在当前 PR 首次新增，因为其可信依据是已批准中心模板和 V，而不是“它在 main 中已经存在”。其他被修改的普通 CI 文件仍不受信。整个独立 run 只允许规范入口调用中心验证器，不能与任意 PR job 混用一个可采信 run。

## 5. 执行流程与候选绑定

1. **解析身份**：可信解析 job 从 GitHub 事件和 API 获取 repository ID、PR 编号、base SHA、head SHA、candidate merge SHA；不从 PR 标题/正文拼装命令。
2. **验证候选**：确认 PR 仍打开、base/head 一致，并校验候选提交的父提交关系。不能在 merge SHA 缺失时降级检查 head。合并队列绑定队列 ref、候选及父提交，不借用普通 PR 的旧结果。
3. **准备输入**：分别检出固定 V 的验证资产和固定候选源码，路径隔离；禁用持久 Git 凭据、子模块和 LFS 自动拉取。路径逃逸、外部链接和超限输入失败关闭。
4. **执行固定检查**：受信控制器在隔离环境执行已登记的检查，候选文件只作为被检查对象。
5. **发布结果**：由受信控制器生成小型结果清单，发布 job 再核对候选新鲜度；缺任何必需项不发布成功结果。
6. **门禁采集**：G 通过 GitHub API 核验来源和清单，形成独立可信证据，再进行既有安全及架构判定。

分支更新会创建新一轮验证。默认总运行上限 10 分钟；审查器沿用有界等待，超时写明“验证尚未完成”，仍 BLOCK。验证随后完成时可以重跑审查；不得复用旧 base/head/candidate 的 PASS。

## 6. 隔离与权限

解析/下载阶段只用本仓库的最低读取权限；验证工作流不接收 `DEEPSEEK_API_KEY`，不用 `secrets: inherit`，不申请写仓库、部署或 OIDC 权限。AI 审查在另一工作流/runner 上运行，不与候选执行共用工作目录。

需要执行候选代码的测试运行在一次性容器中：

- 镜像固定 digest；非 root、丢弃 capabilities、禁止提权，设置 CPU/内存/PID/时间限制。
- 候选源码和可信测试输入只读，临时文件使用独立 tmpfs；不挂载 Git 元数据、runner home、Docker socket 或宿主机结果目录。
- 不传入 GitHub token、Actions runtime token、业务 Secret、代理凭据或 Actions 文件命令路径。
- 测试容器禁用网络，不复用缓存；不执行候选 Dockerfile、本地 Action、npm 生命周期脚本或候选提供的测试启动命令。
- 候选 stdout/stderr 按不可信数据收集；不直接回显为 GitHub workflow commands，不据其声明生成通过结果。超量输出截断并明确标记，不能掩盖失败。

可信启动器负责超时、退出码、预期测试清单/数量、缺失或跳过判定。测试成功只证明受控用例通过，不证明代码没有恶意行为；不把候选自己编写的成功声明升级为独立测试证据。

依赖审计仅将经验证的锁文件数据发送至批准的漏洞查询服务；不安装候选依赖、不执行 scripts，不沿用候选 `.npmrc` 或任意 registry/代理配置。该检查单独运行，不能给执行候选代码的测试容器开放网络。

扫描工具和容器本身也属于信任边界；镜像 digest、工具版本、规则内容与许可证信息需在 V 发布前确定并记录。未确定或下载校验失败时不得接入生产；不得用 `latest` 或动态 `p/javascript` 规则集冒充固定规则。

## 7. 检查能力与覆盖边界

| 独立能力 | 固定输入/规则 | 可满足的逻辑检查 |
| --- | --- | --- |
| Secret 扫描 | 中心规则、候选 Git 快照/规定 diff 范围 | `secret-scan` |
| 静态扫描 | 固定 Semgrep 规则和 CI 配置校验规则 | `sast-config-scan` |
| 依赖审计 | 经验证的候选锁文件，生产依赖策略 | `dependency-scan` |
| 支付退款测试 | 已审核中心测试资产对候选实现 | `payment-refund-tests` |
| 授权测试 | 已审核中心访问控制测试资产对候选实现 | `authorization-tests` |
| 生产配置验证 | 中心固定验证器读取候选配置 | `production-hardening-tests` |

扫描范围由中心配置枚举候选 Git 树决定，不受候选 `.semgrepignore`、`.gitleaksignore`、扫描 suppression 或 PR 新增排除项控制。记录目标数、规则数和跳过原因；空扫描、解析错误和越界路径不得记为成功。图片等明确非源码文件可以按固定类型规则排除，不能借此排除工作流或业务源码。

扫描 CI 文件不执行它们。必须包含权限、Secret 传递、危险触发器、外部 Action 来源和候选命令的静态检查；不能把“中心测试通过”表述为“所有新 CI 命令安全”。

关键测试资产对支付、退款、员工管理等路径建立明确覆盖清单。中心仓库若为公开仓库，不得直接复制私有项目测试或业务源码到其中。可公开的通用测试由中心维护；私有测试仍保留在 `weixin`，由 V 的项目配置登记经过独立审核的测试来源提交、文件清单和内容摘要，在目标私有 runner 中读取。来源可以是已审核的 base 或另行审核的固定测试提交，但不能由本次 PR 自动选择，更不能仅因测试存在于当前 head 就认作可信。

可信测试来源和候选业务源码在准备阶段分别读取、核对摘要并隔离放置，测试基线不能导入候选可替换的测试辅助脚本。目标 PR 新增/修改的测试可作为补充，但不能覆盖或删除这套基线。未建立某关键路径的可信用例时，该项不可用，不用“运行了任意测试”冒充授权验证。

`architecture-owner-approval` 不在自动映射中。JSON 解析成功不等于负责人审批；契约/债务政策修改继续要求独立治理，不借本流程自动批准。

## 8. 结果格式与可信来源核验

受信发布器输出唯一的 `verification.json`，存入固定命名、与 run attempt 绑定的 artifact。采用版本化 schema，包含：

- 仓库 ID/全名、事件类型、PR 编号或队列 ref。
- base/head/candidate SHA；队列模式包含父提交身份。
- verifier 仓库、工作流路径、完整 SHA、profile ID/digest。
- run ID、attempt、Check Suite ID。
- 每个固定 check ID 的状态、扫描/测试计数和经脱敏的原因码。

这是一项明确的采集接口扩展：当前门禁不读取 artifact；新实现仅允许下载通过来源验证的单个小型结果包，不下载完整日志、SARIF 或任意用户附件。

核验必须全部通过：

1. Check App 是预期 GitHub Actions；repository、check suite、run、attempt 和实际 job/check ID 彼此对应。
2. GitHub API 显示匹配事件及源码身份，run 完成且成功；必需 job 均成功，不能 neutral/skipped/取消后凑齐。
3. 运行所用顶层入口内容精确匹配中心规范模板。
4. `referenced_workflows` 的实际仓库、路径、解析 SHA 与批准 V 一致，无未登记嵌套工作流。字段缺失或无法核验时不采信。
5. 验证器/发布 job 的身份和固定结果路径匹配，结果仅来自该 run 的本次 attempt；重跑前遗留或重复命名 artifact 拒绝。
6. artifact 未过期，压缩大小和解压后大小分别不超过 1 MiB，只允许一个普通 `verification.json`；不把归档解压到执行目录，不接受符号链接、路径穿越或多余文件。
7. 清单中所有身份与 GitHub 数据、G 的受信策略及当前候选一致；未知 check ID、重复项、缺字段、伪造计数和未批准 profile 拒绝。
8. 报告发布前再次核对 base/head/candidate；任一变化即旧结果失效。

结果文件自身没有“写了 trusted 就可信”的字段。可信性来自固定入口、实际执行的 V、隔离发布路径和 GitHub 运行元数据的联合验证。候选不能写宿主结果文件，也不能获得上传 artifact 的 runtime 凭据。

实现增加单独的生产者标识 `github-actions-central-verifier`。证据类型和逻辑检查名由中心 check ID 映射，禁止按任意字符串包含 `authorization` 就把它升级成授权证据。原有来源检查不删改为宽松规则。

## 9. 报告与其他阻断

报告分别展示“模型发现”“机器证据缺口”“架构/债务阻断”，日志优先展示实际阻断原因，避免“AI 说风险低，所以为何 BLOCK”的歧义。

独立结果只补充已验证能力，不把整个普通 Quality gates 工作流追认为可信。即便独立验证通过，真实安全风险、契约违规、债务增长或缺少负责人审批仍可 BLOCK。

当前 P2 `ci.trust-boundary` 必须另行核实运行权限、Secret、网络及可利用路径。不得为通过门禁删掉风险、虚构已修复或直接增加预算；也不能仅因标准低权限测试执行 PR 代码就机械认定存在安全漏洞。若确认真实风险则修复并复核；若证据证明误报则在审查规则和回归测试中纠正依据，不添加针对 PR #4 的特殊豁免。

## 10. 发布、接入与回滚顺序

1. 用户审核本文；随后生成和审核实施计划。
2. 实现 V 的验证器、项目配置、固定资产和对抗测试，在中心仓库独立 PR 审核发布。此前中心测试出现过 Actions allowlist 启动失败，必须先确认 CI 能真正运行，不能拿本地结果冒充云端验收。
3. 实现并发布 G，将已批准的 V 固定登记；完成来源伪造和 SHA 过期的拒绝测试。
4. 更新 `weixin` PR #4：保留待审改动，增加规范独立入口、固定 V，并把审查入口固定到 G。无需先合并 PR #4 才能运行新增的普通 `pull_request` 验证入口。
5. 在真实 PR 上检查完整运行元数据及独立证据，处理剩余 P2/架构问题；全部满足后再单独请求该 PR 当前 head 的合并确认。
6. 基线合入后更新员工功能 PR #3，在新候选 SHA 上完整复测。不得照搬 #4 的通过结果。

中心仓库的首次可信发布需要仓库负责人审批；目标 PR 无权批准中心信任根。这个必要的外部审批不能由同一新验证器自行证明。

任一接入步骤失败保留 BLOCK。回滚使用正常追加提交移除新入口或恢复仍受批准的 G/V；不强推、不移动版本标签、不关闭门禁。源码修复与门禁版本回滚分开审查。

## 11. 验收矩阵

| 场景 | 预期 |
| --- | --- |
| 合法 CI 变更、规范入口、固定 V、当前候选全部检查通过 | 独立证据可信；最终仍受 AI/架构/债务裁决 |
| PR 修改普通 quality.yml 为无操作 | 普通结果不可信；中心检查照常执行 |
| PR 修改独立入口/添加 steps/改 V/传入跳过参数 | 来源核验失败，BLOCK |
| 伪造同名 Check、其他 run 的 artifact、旧 attempt 结果 | 不采信，BLOCK |
| base/head/merge 或队列组合变化 | 旧结果失效，新候选重跑 |
| 仅扫描通过，支付/授权基线测试失败或缺失 | 对应证据不足，BLOCK |
| 修改候选忽略文件、删除测试、空扫描、零测试 | 不改变中心基线；不满足时 BLOCK |
| 恶意测试读 token/联网/写可信资产/伪造 workflow command | 隔离阻止；不生成虚假通过证据 |
| 超时、API 403/404、分页不完整、元数据缺失、artifact 超限 | 明确 unavailable，BLOCK |
| 真实 Secret/扫描告警、配置越权、运行时漏洞 | 固定策略检查失败，不能被模型 PASS 覆盖 |
| 独立验证通过但真实 P2 未登记或触发债务增长 | 架构门禁仍 BLOCK |
| 不修改 CI 的现有 PR | 原路径行为保持；新增来源不削弱旧拒绝测试 |

本地单元/集成测试覆盖上述拒绝路径；真实 GitHub 验收覆盖 wrapper、引用 SHA、run/attempt/job/artifact、事件候选绑定和权限隔离。模拟 API 测试不能代替真实运行验证。本阶段是后台 CI 流程，不以 Playwright 页面点击代替安全验收。

## 12. 已验证资料与设计限制

- 本次读取实际 `weixin` run `36364180228`，GitHub 返回 `referenced_workflows`，含中心路径及解析后的完整 SHA；它支持来源核验设计，但不等于证明新验证器已运行。
- [GitHub 可复用工作流权限及引用规则](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations)。
- [GitHub workflow runs API](https://docs.github.com/en/rest/actions/workflow-runs)。
- 具体镜像 digest、动作提交和中心发布 V/G 是实现与发布时必须验证的产物，不在本设计中编造值。
- 所有“受保护”“已审核”都是部署验收项，不根据仓库名称或文件路径推定。没有有效保护时明确报告剩余风险，不作强制安全保证。
